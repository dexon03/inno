# Javers Audit

Аудит змін записів складу поверх проєкту з попереднього завдання.

Ця гілка продовжує [`api-response`](../../tree/api-response), де всі відповіді API зведені до спільної оболонки. Тут додається історія змін: хто, коли і що саме міняв.

За взірець узятий репозиторій з лекції 7 — https://github.com/gprohorov/javers-test.

## Запуск

Потрібні JDK 25 і MongoDB.

```bash
docker run -d --name inno-mongo -p 27017:27017 mongo:7

./mvnw spring-boot:run -Dspring-boot.run.profiles=dev
# якщо 8080 зайнятий:
SERVER_PORT=8081 ./mvnw spring-boot:run -Dspring-boot.run.profiles=dev

./mvnw test
```

Swagger UI: `http://localhost:8080/swagger-ui.html`

Тести: 35 (23 на API, 12 на аудит), усі проходять.

## Два різні аудити, і обидва потрібні

Їх легко сплутати, бо слово те саме, але відповідають вони на різні питання.

**Spring Data** додає до самого запису чотири поля: `createdDate`, `createdBy`, `lastModifiedDate`, `lastModifiedBy`. Це поточний стан — видно одразу, нічого шукати не треба, але історії немає: попереднє значення затирається наступним.

**Javers** зберігає окремо всю послідовність версій запису і дифи між ними. Відповідає на питання «що саме змінилося три правки тому» і «яким цей запис був минулого вівторка».

Перше показує, хто торкався запису востаннє. Друге — що з ним відбувалося весь час. Одне одного не замінює, тож у проєкті є обидва.

## Як це влаштовано

| Клас | Призначення |
|---|---|
| `AuditMetadata` | чотири поля Spring Data; `Item` успадковує |
| `AuditConfiguration` | вмикає обидва механізми і дає їм спільне джерело імені автора |
| `ItemRepository` | позначений `@JaversSpringDataAuditable` |
| `AuditService` | читає історію з Javers і переводить її у власні DTO |
| `AuditController` | чотири ендпойнти історії |

### Ендпойнти

```
GET /api/v1/audit/items                 зміни всіх записів
GET /api/v1/audit/items/{id}            зміни одного запису
GET /api/v1/audit/items/{id}/snapshots  усі версії одного запису
GET /api/v1/audit/items/{id}/pretty     текстовий звіт для людини
```

Усі, крім останнього, віддають ту саму оболонку `meta` + `data`, що й решта API. `/pretty` — навмисний виняток: це текст для читання очима, а не дані для програми.

## Що зроблено інакше, ніж у взірці

### Аудит на репозиторії, а не на методах сервісу

У взірці `@JaversAuditable` стоїть на `create` і `update` в сервісі. Працює, але аудит тоді тримається на тому, що хтось не забуде позначити новий метод. `@JaversSpringDataAuditable` на репозиторії перехоплює всі записи в базу незалежно від того, звідки їх викликали — зокрема й з коду, написаного пізніше.

### Одне джерело імені автора

У взірці Spring Data бере автора з `System.getProperty("user.name")`, а Javers — з `AuthorProvider`, який повертає жорстко вписане `"ADMIN"`. Тобто один і той самий запис підписувався двома різними іменами: у полі `createdBy` одне, в історії змін інше.

Тут обидва беруть ім'я з одного методу. Коли з'явиться автентифікація, міняти треба буде лише його.

Є тест, який це тримає: `recordAndHistoryAgreeOnAuthor` порівнює `createdBy` у записі з автором у історії.

### Службові поля не вважаються змінами

Без цього кожна правка кількості давала б в історії три рядки замість одного: саму зміну плюс оновлення `lastModifiedDate` і `lastModifiedBy`.

Гірше інше. Mongo зберігає час із точністю до мілісекунд, а в пам'яті він мікросекундний. Через це перше ж читання-запис показувало в історії зміну, якої ніхто не робив:

```
createdDate   2026-11-16T13:40:35.191099Z  ->  2026-11-16T13:40:35.191Z
```

Для журналу аудиту це найгірший тип дефекту: запис, що описує правку, якої не було. Поля позначені `@DiffIgnore`, і на тому самому сценарії історія скоротилася з 14 рядків до 7.

### Час у UTC

У взірці поля дат мають тип `LocalDateTime` — тобто час без зони. Для аудиту не годиться: при переїзді сервера в іншу зону чи при переході на літній час записи стають непорівнюваними, а частина взагалі неоднозначною. Тут `Instant`.

### Назовні йдуть власні DTO

Взірець віддає `javers.getJsonConverter().toJson(changes)` — внутрішню структуру Javers із `globalId`, `commitMetadata` і службовими типами. Це чужий формат, не пов'язаний з рештою API, і контракт, що зміниться разом із версією бібліотеки. Тут є `AuditChangeResponse` і `AuditSnapshotResponse` з тим, що справді потрібно.

### Обмеження на розмір відповіді

Історія лише росте. Запит, який сьогодні повертає десяток рядків, за рік поверне десятки тисяч. Усі ендпойнти аудиту мають параметр `limit` з обмеженням у 500.

## Окрема база для історії

Це те, на що вказує примітка до завдання: «Attention to application.properties. Additional DataBase settings».

Правильний префікс — `javers.mongodb.*`. Перевірено за `spring-configuration-metadata.json` у `javers-spring-boot-starter-mongo-7.11.10.jar`:

```properties
javers.mongodb.host=localhost
javers.mongodb.port=27017
javers.mongodb.database=inno-audit
javers.new-object-snapshot=true
```

У взірці лекції стоїть інше:

```properties
spring.javers.mobgodb.host=localhost
spring.javers.mobgodb.port=27017
spring.javers.mongodb.database=item-audit
```

Тут два відхилення від робочого варіанта: зайвий префікс `spring.` і друкарська помилка `mobgodb` замість `mongodb` у двох рядках із трьох. Такі ключі Spring мовчки ігнорує — помилки не буде, просто налаштування не застосується.

Я не став вгадувати наслідок, а перевірив. Підставив назви з лекції, створив і змінив запис, подивився, що в базах:

```
inno.jv_snapshots   документів: 10     <- історія лягла сюди
inno.jv_head_id     документів: 1
inno.items          документів: 9
inno-audit:         (бази немає)
```

Тобто база `inno-audit` навіть не створюється, а колекції Javers осідають поряд із самими записами. З правильними назвами:

```
inno.items              документів: 8
inno-audit.jv_snapshots документів: 12
inno-audit.jv_head_id   документів: 1
```

Розділення тут не косметичне. Історія змін росте необмежено і має інший профіль доступу, ніж робочі дані: пишеться завжди, читається зрідка, не видаляється ніколи. Тримати її поряд з основною колекцією означає, що бекап, права доступу й політика зберігання в них будуть спільні, хоча мають бути різні.

## Як це виглядає

Запис створили з кількістю 5, потім змінили на 9, потім на 2:

```
GET /api/v1/audit/items/{id}

коміт  11  quantity   9        -> 2
коміт  10  name       Кава     -> Кава мелена
коміт  10  quantity   5        -> 9
коміт   9  id         null     -> 6afb07f83b4a48f9f519b122
коміт   9  name       null     -> Кава
коміт   9  code       null     -> 000500
коміт   9  quantity   null     -> 5
```

Той самий запис у вигляді версій:

```
GET /api/v1/audit/items/{id}/snapshots

v3  UPDATE   Кава мелена   к-сть=2   dmytromochalov
v2  UPDATE   Кава мелена   к-сть=9   dmytromochalov
v1  INITIAL  Кава          к-сть=5   dmytromochalov
```

Після видалення додається `v4 TERMINAL` — запису вже немає, але слід від нього лишився.

## Тести

12 перевірок саме на аудит. Він небезпечний тим, що нічого не повертає викликачеві: якщо перестане записуватися, жоден інший тест цього не помітить, і виявиться це тоді, коли історія знадобиться — тобто коли вже пізно.

Що перевіряється:

- створення, зміна і видалення потрапляють в історію (`INITIAL`, `UPDATE`, `TERMINAL`);
- кожна правка додає рівно одну версію, а правка без фактичних змін не додає жодної;
- зберігається старе значення поля, а не лише нове;
- службові поля не потрапляють в історію як зміни;
- історії різних записів не змішуються;
- запис і його історія підписані тим самим іменем;
- відповіді аудиту мають ту саму оболонку, що й решта API;
- завелике обмеження відхиляється.
